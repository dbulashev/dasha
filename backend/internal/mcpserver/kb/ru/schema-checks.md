# Проверки схемы

Что возвращает `schema_lint`, по кодам. API отдаёт коды и числа, текст —
ваш. Все проверки читают только системный каталог, пользовательские данные не
затрагиваются.

Уровни: `error` (чинить), `warning` (чинить скоро), `notice` (стоит знать).
Уровень назначается по фактам, пороги настраиваются — доверяйте полю `level`,
а не запомненным числам.

Два поля определяют, можно ли вообще верить отчёту:

- `skipped` — проверки, которые НЕ выполнялись, с причиной
  (`insufficient_privileges`, `unsupported_version`, `disabled`, `error`).
  Проверка из этого списка не говорит о схеме ничего. Нельзя писать «всё
  чисто», пока список непуст, не назвав, что именно не проверялось.
- `truncated` — проверка упёрлась в лимит строк, счётчики занижены.

В `schema_lint_summary` то же правило действует на уровне базы: `skipped` — число
не выполнившихся там проверок, `failed` — база, которую не удалось прочитать
вовсе. Нули означают «чисто», только когда оба пусты.

`params.partitions` означает, что находка уже схлопнута до родительской таблицы
и покрывает столько партиций. Действовать нужно на родителе — PostgreSQL всё
равно откажет в починке отдельной партиции.

## sequence_exhaustion

`params`: `used_pct`, `last_value`, `max_value`, `owned_by`, `owned_column_type`.

Уровни по остатку свободных значений: < 5% error, < 10% warning, < 20% notice.
Если владелец — колонка `integer`, уровень поднимается на ступень. Пороги
настраиваются через `schema_lint.sequence_thresholds`; health-правило
`sequence_exhaustion` читает ту же настройку и стоит на тех же точках, но
ступень для int4 не применяет — его уровень может быть на единицу ниже. Не
называйте порог, которого не прочитали здесь.

`max_value` — реально действующий потолок, не всегда собственный потолок
последовательности: bigint-последовательность, привязанная к колонке `integer`,
ломается на 2147483647, когда переполняется колонка.

Первое действие: расширить последовательность (`ALTER SEQUENCE … AS bigint`).
Если `owned_column_type` = `integer`, одного этого НЕДОСТАТОЧНО — придётся
менять и тип колонки, а это переписывает таблицу и требует окна. Так и надо
сказать, а не цитировать один ALTER SEQUENCE.

## no_primary_key / no_unique_key

`no_primary_key` — PK нет, но есть пригодный уникальный индекс.
`no_unique_key` — нет ни того, ни другого. Оба `error`.

`params.unique_nullable = true` означает, что уникальный индекс построен по
nullable-колонке: как REPLICA IDENTITY он не годится, поэтому совет «у вас же
есть unique» для логической репликации будет неверным.

Последствия, которые стоит назвать: логическая репликация не реплицирует
UPDATE/DELETE без replica identity, pg_repack отказывается работать с таблицей,
а из пары одинаковых строк нельзя удалить одну.

Первое действие: сначала выяснить, что это за таблица. У staging- или
append-only-таблицы ключа может законно не быть.

## public_create_privilege

`params.owner`. `error` на PG 15+, `warning` на PG 14, где открытая схема
`public` — заводской дефолт: риск тот же, просто его не выбирали.

Любой пользователь может создать объект, который перехватит обращения по
`search_path` (CVE-2018-1058).

Первое действие: `REVOKE CREATE ON SCHEMA <schema> FROM PUBLIC;`

## unlogged_relation / unlogged_sequence

`warning`. Содержимое не переживёт аварийную остановку и не попадёт на реплики —
на standby такая таблица всегда пуста. Для временных данных это осознанный
выбор; проблема, когда кто-то рассчитывает найти там строки.

Первое действие: `ALTER TABLE … SET LOGGED` (переписывает таблицу), если данные
должны выживать.

## uuid_in_non_uuid_type

`params`: `column`, `column_type`. `notice`.

Эвристика по имени колонки и объявленной длине (32/36 символов), а НЕ факт —
так и нужно сказать. Если догадка верна, `uuid` стоит 16 байт против 36 — и в
таблице, и в каждом индексе по этой колонке.

## relation_without_fk

`notice`, выключена, пока не включена в конфигурации. Таблица не участвует ни в
одном внешнем ключе: либо забыта, либо связи живут только в коде приложения.
На схемах, где FK не используются принципиально, это шум.

## relation_without_columns

`notice`. Все колонки удалены или не были добавлены. Данных не хранит, но
попадает в дампы.

## reserved_word_in_name / unsafe_chars_in_name

`reserved_word_in_name` (`warning`) — имя объекта совпадает с зарезервированным
словом SQL: без кавычек запрос падает или разбирается не так, как задумано.
`unsafe_chars_in_name` (`notice`) — в имени есть символы вне `[A-Za-z0-9_]`
(точка, пробел, дефис, кавычка, не-ASCII), цитировать придётся везде. Заглавные
буквы намеренно не отмечаются: это стиль именования, а не поломка.

Проверки только про ломающиеся инструменты, не про стиль. Лечение —
переименование, то есть миграция; так и надо сказать, а не подавать это как
бесплатную операцию.

## invalid_constraint

`params`: `constraint`, `referenced_by`. `warning`. Ограничение создано как
NOT VALID: оно применяется к новым строкам, но существующие данные никто не
проверял, и планировщик на него не опирается. То, что выглядит как соблюдаемая
целостность, ею не является.

Первое действие: `ALTER TABLE … VALIDATE CONSTRAINT …` — читает таблицу
целиком, но берёт слабую блокировку и не мешает ни чтению, ни записи.

Те же строки, что на странице анализа внешних ключей: отчёт — второе
представление, а не второй источник.

## fk_type_mismatch / fk_nullable / fk_similar

Тоже со страницы анализа внешних ключей. `params`: `constraint`,
`other_object` (ссылочная таблица, покрытые колонки или второй ключ).

`fk_type_mismatch` (`warning`) — у двух сторон ключа разные типы колонок. Каждая
проверка целостности выполняет приведение, из-за чего индекс на стороне родителя
может выпасть из плана. Лечение — `ALTER TABLE` с переписыванием таблицы; об
окне надо сказать прямо.

`fk_nullable` (`notice`) — колонки ключа допускают NULL, поэтому при MATCH SIMPLE
строка с NULL проходит проверку целиком. Дефект только если связь задумывалась
обязательной — сначала спросите, потом предлагайте NOT NULL.

`fk_similar` (`notice`, по умолчанию выключена) — два ключа по пересекающимся
колонкам на одну цель. Кандидат на разбор, а не вердикт.

## index_similar / btree_on_array

Из анализа индексов. `params`: `index`, `other_object`.

`index_similar` (`notice`, по умолчанию выключена) — два индекса, совпадающих
после нормализации определения. Индекс, обслуживающий ограничение, напрямую не
удаляется: сначала снимается ограничение.

`btree_on_array` (`notice`) — btree по колонке-массиву работает только для
сравнения массива целиком. Если ищут по элементам, нужен GIN; если сравнивают
массивы целиком, индекс уместен, а находка — шум.
